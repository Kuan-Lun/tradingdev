# TradingDev 軟體需求規格

本 SRS 定義目前產品的需求基線與驗收入口，適用版本由本文件所在的 Git commit
識別。需求、詳細契約與實作應一致；發現差異須核實需求，不直接以實作現況改寫承諾。
本文件不是測試通過證明、功能開發路線圖，也不宣稱經過外部標準認證。

## 1. 目的與範圍

讓研究者透過支援 MCP 的 LLM 客戶端，把交易構想轉為可檢查的策略，執行歷史研究，
並取得可追溯、可解讀及可保存的成果。範圍包含策略建立與修訂、行情與特徵、回測、
固定參數比較、walk-forward、參數最佳化、獨立 ML 訊號研究及成果查詢／交付。

產品不提供真實下單或獲利保證，不提供對話模型；生成 Python 的驗證不是安全沙箱。
既有能力的限制屬本基線；未核定的新能力不因寫入提案或研究筆記而成為產品承諾。

## 2. 利害關係人與使用者

| 角色 | 需要達成的工作 |
| --- | --- |
| 策略研究者 | 用白話提出構想、確認研究選擇、解讀與保存結果；不要求預先懂工具名稱或替策略命名 |
| 策略作者與整合者 | 依正式契約提供 Python／YAML，透過 MCP、CLI 或 Python 服務使用能力 |
| 部署維運者 | 設定可用環境與工作區，管理連線入口、資料保存及程序 |
| 成果讀者 | 在不重跑策略的情況下閱讀報告、核對設定與證據限制 |

LLM 客戶端、行情服務與瀏覽器是外部系統。模型負責需求理解與說明；後端負責可機械
驗證的設定、身分與狀態，不把工具參數當成人類已閱讀或同意的證明。

## 3. 產品觀與名詞

MCP 是主要產品介面；CLI 提供明確執行入口，Dashboard 呈現已保存結果。
各入口共用相應 application services，但不保證功能或互動流程完全相同。
部署方式與平台條件見 [README](../README.md#安裝與連接助手)，責任分工見
[架構](../ARCHITECTURE.md#系統邊界與模組責任)。

| 名詞 | 需求層意義 |
| --- | --- |
| 策略 revision | 固定策略程式與基礎設定的版本，具有自己的驗證證據 |
| Execution manifest | 某次執行的固定策略身分與有效設定 |
| Execution plan | 結合固定設定、檢查證據及確認內容的執行計畫 |
| Job／run | 背景工作及保存結果的身分；直接回測 CLI 不建立背景 job，固定比較另有父子關係 |
| Artifact | 可探索、讀取及交付的保存產物 |
| ML dataset／model | 獨立的資料版本及模型身分，不等同策略 revision 或回測 run |

## 5. 使用案例

| 案例 | 正常流程與完成條件 | 主要替代／失敗路徑 |
| --- | --- | --- |
| UC-01 從構想到回測 | 釐清四項研究選擇 → 新建／修訂生成策略時保存 revision，通過程式品質驗證及合成訊號 dry-run 取得執行資格；使用既有內建策略時準備檢查其設定、模式及參數 → 交付確認單 → 後續同意 → 執行並保存 → 交付結果及報告 | 缺項先追問；驗證失敗修訂；拒絕不執行；修改重新確認；執行失敗可查原因 |
| UC-02 比較與樣本外研究 | 選擇固定比較、walk-forward 或最佳化 → 核對模式、期間及設定 → 確認 → 固定比較對照共用條件下的指定候選；walk-forward 與最佳化另解讀其樣本外證據 | 模式不支援或期間無效時拒絕；無有效候選不能宣稱找到最佳參數 |
| UC-03 找回歷史研究 | 選定工作區與結果 → 查設定、指標及紀錄 → 以保存內容產生報告 | 缺少或損壞證據明示，不以目前設定重建歷史或悄悄重跑 |
| UC-04 獨立 ML 訊號研究 | 探索可用能力 → 以 `ensure_data` 取得或確認行情 → 讀取可重用快取建置資料集 → 模型或手設規則 → 評估、排名及報告 | 資料不可重用、對齊錯誤或比較條件不同時明示；不自動轉成交易策略 |
| UC-05 保存與分享 | 保存研究摘要 → 選定版本與報告 → 匯出可獨立閱讀封存 | 版本衝突先核對；附件遺失或變更拒絕匯出；遠端本機路徑不視為可下載網址 |

UC-01／02 的對話確認適用於 MCP 執行計畫，包括 `tradingdev-codex` 對話入口。
直接回測 CLI 命令本身是執行請求，UC-04 不使用該確認計畫或背景回測流程。
確認語意見[執行計畫契約](execution_plans.md)；各分冊的驗收條件保留這些差異。

## 6. 功能性需求

各分冊的 `FR` 條目是正式功能需求；每條包含適用行為、可觀察驗收、詳細契約與驗證
入口。編號表示穩定身分，不表示優先順序、完成狀態或測試覆蓋率。需求移動時保留編號。

## 7. 非功能性需求

`NFR` 條目按責任放在品質、介面及成果分冊。執行期限與容量依正式定義維護，不手抄數值清單。
目前沒有跨任意硬體、資料量與模型的統一延遲或吞吐量承諾；效能目標若要成為需求，
須先固定環境、工作負載、量測方式及驗收門檻。

## 8. 資料需求

策略版本、執行設定、結果與衍生報告須有可核對的關係；資料缺失與零值分開表示。
Workspace 保存研究成果，與 Git 管理的 bundled strategies 分離。資料模型及保存
語意由[執行產物](run_artifacts.md)、[績效產物](performance_artifacts.md)及
[ML 契約](ml_research.md)負責；SRS 不另列完整欄位或資料庫 schema。

## 9. 介面需求

標準 MCP 提供探索、操作與按需契約；不能假設客戶端可讀 server 本機檔案。
CLI、Dashboard、HTTP／stdio 及成果交付的適用差異由介面、共通品質與成果需求約束。
精確參數、型別、列舉及預設值以工具 schema、正式模型與其契約入口為準。

## 10. 限制與假設

行情可用性受外部來源限制；成功取得不證明 K 棒齊全或資料永不修正。
生成程式檢查不證明符合自然語言構想、沒有前視偏誤或安全隔離；樣本內排名不證明
樣本外表現。來源 hash 與固定設定提供追溯，未完整封存環境，因此不保證跨環境完全重現。
平台、信任邊界與保存限制詳見共通品質需求及各契約。

## 11. 驗證方式

每條需求的驗證欄指向既有測試或明確人工操作；引用只是可執行的查核入口。
Service、domain 測試檢查業務行為；真實 MCP／worker 測試檢查程序與協定；
真實模型情境檢查工具探索與多回合互動；瀏覽器人工驗收檢查閱讀及操作。
離線測試通過不能替代真實模型或瀏覽器驗收，也不代表所有平台已驗證。
本 SRS 不保存易過期的「已通過」標籤，當次結果記錄於對話及 PR。

## 12. 追溯方式

「使用案例 → 功能分冊 → 需求編號 → 契約／驗證入口」形成追溯關係。
每條需求旁的引用是唯一維護的明細，不另外手抄一份逐條追溯表。
開發檢查會核對結構、導航、引用及審查責任，語意一致性與能力限制另由候選審查確認；
工具的實際保證見[開發指南](development.md#srs-維護與檢核)。

## 13. 風險與緩解

| 風險 | 需求中的處理與剩餘限制 |
| --- | --- |
| 誤解構想或擅自選定研究設定 | 必要輸入追問、白話確認及來源保存；後端不能證明程式與構想等價 |
| 前視、過度擬合或混淆評估口徑 | 時間切分與標籤重疊檢查、樣本外證據及比較限制；仍需研究者判斷 |
| 設定漂移、來源損壞或誤認工作完成 | 固定執行身分、完整性核對及可查詢狀態；不宣稱跨資源交易或對惡意寫入者的防護 |
| 成果遺失或意外洩露 | 保留工作區、明確交付與獨立封存；隱藏報告章節不會移除內嵌資料 |
| 文件漂移 | 結構檢查與按責任提供原文的語意審查；模型審查仍可能漏判 |

## 14. 交付件

Repository 提供產品程式、操作指南、架構與正式契約，以及本 SRS。
研究交付依操作包含策略版本、固定設定、工作／結果身分、指標與限制、HTML 報告及
明示要求的筆記封存。報告或封存不等同完整可重現環境；不能以中途工具訊息取代最終交付。

## 15. 整體驗收

以 UC-01 至 UC-05 選取適用場景，逐一核對各分冊需求，涵蓋缺項、拒絕、修改、
執行失敗、取消、歷史缺證據及成果保存。驗收結果須標明版本、入口、環境、實際
執行的檢查與未驗證範圍；未取得證據的需求保留待驗證，不因文件或測試數量而視為完成。
