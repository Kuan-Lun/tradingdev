我是國立臺灣大學資訊工程學系計算理論暨金融計算實驗室的一員。許多成員的研究與金融交易相關，因此希望建立共用的後端，協助大家開發自己的策略。 共用的對象是研究所需的基礎能力，各位成員仍能研究自己的策略構想。接下來先說明這個目標需要哪些能力，再看現有工具能提供什麼。

共用實驗基礎需要清楚區分各自的策略、版本及結果，並保存重現實驗所需的設定與依據。多樣的策略與模型包含交易規則、統計方法及機器學習模型的建構，以及適用的訓練與驗證。 策略回饋應引用檢查與實驗證據，協助提出修改，再驗證修改是否有效。 AI 開發助手從多位使用者的策略開發紀錄中辨識共通問題與需求，自動產生後端改進方案及程式修改，執行測試並依結果繼續修正。通過審查後，將適合共用的檢查、元件或流程改善整合回後端，支援下一輪研究。 這些是目標能力。目前已有回測與研究紀錄等基礎，多人服務身分、權限及自動工程回饋仍待開發。以下以這些需求檢視現有工具與整合責任。

回測是用歷史行情模擬交易規則。現有工具已能完成許多計算與研究工作，TradingDev 也沿用其中的成熟套件。 Freqtrade 是含回測、最佳化及交易功能的應用。cloudQuant/backtrader-mcp、bcosm 也支援自訂策略，後段逐一比較。QuantConnect 平台已涵蓋完整研究流程，不能把它描述成只有回測引擎。

QC 是 QuantConnect。這頁依四項研究需求，列出官方文件已說明的能力與本專案的研發方向；逐項工具的操作方式與使用情境留在後段。 QuantConnect 已提供專案回測、結果管理與 ML 研究；Agents 能依工具結果繼續研究，並接收回測診斷。VBT PRO MCP 能讓助手執行與修改 Python 回測程式。 自動迭代列中的專案記憶與共用程式庫，是經驗保存與元件重用的相關能力，不等同於自動修改平台後端。此處不據此判定其他產品能否完成後端自動改進，也不宣稱右欄能力是 TradingDev 獨有。 現有方案能否直接滿足特定研究需求，仍須以案例驗證。右欄列的是本專案希望建立與評估的能力，不是已測得的功能或效能優勢。 來源：本頁頁尾的官方文件，查核於 2026-10-30。

研發重點是讓研究證據持續支持判斷與改進。成熟回測工具提供計算基礎，接下來要用具體案例驗證 AI 是否提出有依據的實驗、找回適用的研究經驗，以及產生能解決共通問題的後端修改。 這些是待驗證的研發課題。現有實驗與紀錄可作基礎，研究引導、跨研究記憶及自動工程回饋的進度與限制，在後續頁面分別說明。

後端除了接收工具請求、執行計算和保存資料，也提供模型可讀取的研究流程指引、策略契約與診斷。使用者不必自己把一次次實驗的程式、設定和結果拼回來。 診斷先提供規則式提示，外部 LLM 的報告解讀須保留觀察依據與限制，研究建議不會自動啟動新實驗。研究筆記可保存階段摘要及引用報告，目前尚未完成跨研究自動檢索與後端自動改進。 TradingDev 不內建對話模型。這些能力是研究後端的現有基礎，不代表已提供多人權限或完整執行隔離。 基礎計算包含行情、技術指標、回測與參數研究，採用 VectorBT、TA-Lib、QuantStats 等套件，沒有把 Freqtrade 整合為依賴。ML 訊號研究是現有能力，並非本專案獨有，也不代表已有任意模型支援或真實下單。 ML 模型包含 XGBoost、LightGBM、CatBoost 方向模型；QuantConnect 也提供機器學習研究，支援更多常見框架。模型種類不代表較泛用。 基礎計算與 ML 來源：pyproject.toml、src/tradingdev/domain/ml/models/registry.py；https://www.quantconnect.com/docs/v2/writing-algorithms/machine-learning/popular-libraries/pytorch 研究指引來源：src/tradingdev/mcp/prompts.py 的 SERVER_INSTRUCTIONS、server.py 的 instructions 註冊，以及 tools/strategy.py 的按需契約。

這些是依現有能力提出的使用情境，不是已完成的客戶案例。教學重點是如何檢查假說，不是比較誰的回測收益最高。 團隊可以沿用自己的資料、實驗格式與檢查規則，再將驗證過的共用規則改進到服務中。初期可在可信環境採獨立部署；同一 server 的 workspace 不是現成的多租戶或執行安全隔離。 公司可將研究後端接到既有 AI 入口，由產品入口選擇對話模型、計量 token 用量及安排收費，行情、主機與結果保存則由整合者安排。公開多人服務仍須另行開發權限、隔離與資源管理，收費上線前也須核實依賴及行情授權。 個人助手、公司模型服務及私有部署並非 TradingDev 獨有；QuantConnect Private Cloud 也有公司資料與運算的方案，後段比較其整合責任。 來源：README 的 MCP 連接方式與執行限制、ARCHITECTURE.md 的產品邊界與整合層分工。

研究不是泛稱投資分析。此處具體指策略程式的建立、檢查、歷史回測、參數實驗、時序驗證與結果查詢。 指引由後端提供，推理與互動由使用者選擇的 AI 客戶端承擔。直接在 Codex 開發策略時，Codex 就是這個角色，不需要另建一套助手服務。實際呈現與指引採用方式由客戶端決定，不能把提示詞當成所有客戶端必然遵循的保證。 來源：src/tradingdev/mcp/prompts.py、server.py 與 tools/strategy.py。

本頁保留使用者只有均線交易構想的情境，以具體問句展示 TradingDev 的指引如何影響前端互動。表中的問題可分散於多輪對話，不是要求一次問完；補齊必要研究選擇後，再釐清策略細節與提出方案。這是依現有指引編寫的示意，不是真實模型逐字紀錄或已執行的回測。 提示詞引導由 TradingDev 的 server instructions、工具說明與按需策略契約提供；此處不是指另行註冊的 MCP prompts，也不是固定問卷。實際問句與互動由 Codex 等客戶端的 LLM 組織。 建立新研究前，構想、標的、回測期間與 K 棒頻率缺項時須追問，不能從範例猜出選擇。只有明確要求沿用已選定研究時，才可繼承其設定。 策略具體化包含整理進場、持有、出場與交易方向，確認參數並形成可驗證的程式。模型可提出有說明依據的方案，不能把自己的假設冒充使用者要求。 本金與成本未指定時可依共用模擬政策解析，明示有效值優先。前端須呈現後端產生的確認摘要與 HTML，待使用者明確同意該方案才提交執行。這些是歷史回測假設，不是即時費率或真實下單設定；本金與交易規模依執行模式適用。 提示詞要求不保證所有客戶端一定遵循；後端另檢查必要欄位、設定與執行狀態，但不能證明輸入或同意真的來自使用者。 來源：src/tradingdev/mcp/prompts.py 的 SERVER_INSTRUCTIONS、server.py 的 instructions 註冊，以及 src/tradingdev/domain/strategies/templates.py 的 research 契約與 src/tradingdev/domain/research_policy.py。

承接上一頁的均線策略，假設使用者已確認並完成一次歷史回測，再詢問虧損與修改方向。對話是依實作編寫的情境示意，不是真實模型逐字紀錄，也沒有宣稱本例已測得虧損、回撤或改善效果。 查詢證據：get_run_metrics 回傳保存的指標、定義、有效設定及不可用原因；get_run_trades、get_run_equity 等工具讀取對應執行範圍的原始紀錄。TradeHistoryService 與 PerformanceStore 核對保存資料的身分與完整性，查詢不會重新執行策略。缺少資料須保留原因，不能當成零或由模型猜測。 規則式診斷：DiagnosticService 讀取保存的結果，交給可替換的 DiagnosticProvider。目前的 MaverickDiagnostics 依六項固定門檻提供數值依據、建議檢查及限制。例如 signal 模式的最大回撤超過 0.25，會提示先檢查回撤期間的交易，再以原策略為基準比較明確的出場或風控變體。門檻不是使用者風險上限，也不證明出場規則就是虧損原因；診斷沒有直接找出虧損期間或完成市場情境、波動敏感度的因果分析。 AI 分析指引：SERVER_INSTRUCTIONS 要求先讀診斷，涉及特定虧損期間時再查交易或權益資料；解讀須包含 summary、observations、hypotheses_and_limits、next_steps 與精確的 run_id/scope 引用。文字推理由前端 LLM 完成，後端沒有自行呼叫另一個模型產生評語。新比較須另提可確認的方案，研究建議不授權自動執行。 報告保存：generate_report 接收模型的結構化分析，ReportService 核對引用是否屬於所選報告結果，將分析與規則式診斷保存在 HTML 及 manifest。計算證據與 LLM 解讀分開呈現，沒有解讀時明確標示；引用檢查不等於證明文字推論正確。歷史結果只支持檢驗假說，不保證未來有效。 來源：src/tradingdev/mcp/prompts.py、mcp/tools/runs.py、mcp/tools/history.py、app/diagnostic_service.py、adapters/reporting/maverick_diagnostics.py、app/contracts/reports.py、app/report_service.py，以及 docs/reports.md「Research interpretation and diagnostic providers」。

讀作 MCP，不是 MPC。表中列的是責任，不是要求使用者部署三套系統。直接在 Codex 中開發策略時，Codex 承擔 AI 客戶端角色；TradingDev 不限定對話介面，也不內建對話模型。 TradingDev 以 server instructions、工具描述與按需契約提供研究指引，並由後端強制檢查可機械驗證的輸入與執行條件。客戶端決定互動與推理方式，提示詞不能保證模型遵循，也不能證明使用者真的閱讀或同意。 來源：src/tradingdev/mcp/server.py、prompts.py、tools/strategy.py，以及 ARCHITECTURE.md。

這頁承接使用者、AI 客戶端與 TradingDev 的責任分工，說明部署時可安排的部分。回測可以由資源較充足的主機負責，不代表已提供多節點叢集或大型租戶平台。 目前 HTTP 預設綁定 localhost，另一台設備不能直接使用該主機的 localhost 位址，需另行設定網路轉送與存取控制。對話、模型及收費留在客戶端整合層，後端不綁定特定 LLM。 整合者可以維護自己的研究服務、檢查、策略契約及輸出，但需承擔相應的開發與驗證責任；使用現有服務時仍須遵守其確認流程與後端檢查，不能把可自訂解讀成可在對話中略過授權。 來源：README「手動啟動並使用 HTTP 連接」、ARCHITECTURE.md。

新策略會保存版本，通過驗證及 dry-run 後才取得執行資格；其中的訊號檢查使用固定合成資料，並非歷史回測。準備確認單時只做離線程式與設定檢查，以及適用的合成訊號檢查。單次準備的內建策略不在此時執行訊號；固定參數比較則對每組候選（包含內建策略）執行 80 與 240 根合成 K 棒的訊號檢查。確認前不取得真實行情、不訓練模型、不執行歷史回測；行情、訓練及績效須同意後才開始驗證。 這些步驟已有 SERVER_INSTRUCTIONS 引導，並搭配工具說明及 get_strategy_contract 的按需內容。缺少必要研究選擇時須追問；保存研究筆記須有保存或分享需求。客戶端可安排自己的互動方式，但工具仍會檢查契約與執行狀態。 來源：src/tradingdev/mcp/prompts.py、tools/strategy.py、README「完成第一次回測」與 docs/strategy_contract.md。

這是與僅選擇固定模板的工具相比可具體展示的差異，但不是所有 MCP 專案都只支援模板。cloudQuant/backtrader-mcp 和 bcosm 也支援自訂策略，後面分別比較。

確認前不取得真實行情、不訓練模型、不執行歷史回測；自建策略適用的訊號檢查只用固定合成資料。單次準備的內建策略只檢查設定、執行模式與參數；固定比較的每組候選則都要通過 80 與 240 根合成 K 棒的訊號檢查，包含內建策略。一到八組普通回測的固定候選可共用一份確認單，使用者批准整組後才執行；這不包含需要訓練或 walk-forward 的多組比較，也不會自動擴大搜尋。修改候選或設定後要準備新的計畫並重新確認。後端依賴助手如實轉交使用者決定，不能獨立驗證決定的人類來源。這項限制留在講者稿，操作細節以 README 為準。 來源：README「完成第一次回測」、docs/run_artifacts.md 的 execution plans。

結果主要供 LLM 查詢和分析。詳細交易、帳戶序列與執行紀錄可分頁查詢；不存在的舊紀錄不能靠助手猜測重建。 SERVER_INSTRUCTIONS 要求先讀 get_run_diagnostics，再以 summary、observations、hypotheses_and_limits、next_steps 及精確的 run/scope 引用提交分析，保留於 HTML。generate_report 的工具說明與 ReportAnalysis schema 也公開這個結構。後端提供規則式診斷並核對引用，文字推理由客戶端模型產生，未提供時會標示；不是後端自行呼叫另一個 LLM。涉及特定虧損期間時須先查交易或權益資料，不能只憑摘要判定原因。 來源：src/tradingdev/mcp/tools/history.py、runs.py 與 mcp/prompts.py。

strategy/revision、plan、job、run 的用途不同。job 用於進度與取消，run 用於已保存結果；現有 ID 是追蹤基礎，不等於已綁定使用者擁有權。固定比較以同一份行情快照獨立執行各組普通回測，使用各自資金與策略實例，不合併成一個投資組合。完整比較報告依父工作選取所有候選，包含失敗、取消及未執行的原因；成功結果可點選查看明細。 來源：ARCHITECTURE.md 的 strategy identity 與 run artifacts。

重點是基礎功能有被整合，不把底層套件當作功能不足的對手。Freqtrade 本身已提供很多產品功能，不能說使用它一定要從頭自行組裝。 原版 Backtrader 主線更新停在 2023 年，社群分支持續修正。維護情況依分支而異，不用 issue 數量推論品質。 來源：https://github.com/cloudQuant/backtrader/blob/development/CHANGELOG.md 、 https://github.com/backtrader2/backtrader/issues/98

不能說 VectorBT PRO MCP 只能查文件，或不能開發策略。它也有可由助手讀取的研究 skills。其公開設計不能直接當作完整多人後端，但每人獨立環境是可能的。

MaverickMCP 有自己的優勢，包括模板便利性、Monte Carlo 與 ensemble 工具。不要把自然語言解析成模板說成不能做任何策略研究。 所查 MCP 介面未見等價的新策略原始碼保存、revision 驗證及持久背景 job 生命週期。這是介面範圍比較，不是斷言開發者不能擴充原始碼。

cloudQuant 與 QuantConnect 是不同專案。它有持久工作、取消及日誌，與 TradingDev 的部分功能相近。移入策略時要依各自格式改寫，對話追問能力則取決於結果查詢的範圍。 獨立的 backtrader-skills、backtrader-agent 另有流程與有限 sweep 經驗保存，不能自動視為主 MCP repository 已整合的功能。

bcosm 的驗證工具有 verdict/reasons，流程範例放在 examples/agent_workflow_demo.py。未註冊 prompts 不能簡化成完全沒有引導。 save_run 接收呼叫端提交的 metrics/code/params，與 TradingDev 固定實際執行設定、保存產物的流程不同。

LEAN engine 為 Apache-2.0，可自行建置；官方 CLI/Local Platform 與 Private Cloud 有各自方案條件。不要把官方 remote MCP 的付費 Agent Node 要求套到所有自行使用 LEAN 的情境。

QC 已有新策略建立、編譯、回測、最佳化及結果診斷，不能宣稱 TradingDev 的完整研究流程對 QC 也是獨有。 本頁表達工作方式與維護責任。要主張某個情境更省事或成本更低，仍需具體部署評估。

舉例：「公司已經有和客戶聊天的 AI，只缺一套能真正跑策略實驗的工具。」這比抽象的自由度更容易理解。 需要私有資料時 QC Private Cloud 也可行，不能用資料是否留在公司作單一判準。

現有工具提供可採用的研究能力，也提供評估設計的參考。本專案以研究決策、經驗累積與後端改進作為持續研發方向，成效須由具體研究案例與修改前後的證據驗證。 既有能力與未來目標分開說明，不把記憶、Agents 或可自架說成市場獨有功能，也不以採用的工具數量代表研究價值。

兩種整合共享研究證據，但目的與工程責任不同。工程回饋改善開發工具，策略配置研究整體資金與風險。

可以讓觀眾想像「前一個人踩過的坑，成為下一個人的防護」。這不是自動分享私人策略，也不代表系統已會自行修改並發布核心程式。

外部開發流程可以獨立掛接，實際修改是否涉及核心程式，仍取決於所發現的問題。抽象出的共用能力也需要測試與審查。 現有 record_feature_request、revision 與 run 可作輸入，並未完成自動提案與程式整合。

現有身分 ID 是未來權限設計可用的基礎，尚未完成使用者隔離。此頁集中區分已提供的產品能力與未來方向。 規則式診斷、外部 AI 解讀及研究筆記，已能支持研究判斷與成果續用。右欄進一步擴充分析深度、自動檢索與工程回饋，不把現有紀錄與解讀能力一併列為未來功能。AI 解讀由外部助手提供，未提供時報告會標示，建議不會自動啟動新實驗。 現況來源：README「在對話中查詢」「保存研究筆記與打包分享」，ARCHITECTURE.md「績效計算與對話摘要」「研究筆記與可攜封存」。

以下目標保持簡短。之後可指定「閱讀 TODO-04 再調查與開發」，開始時仍需重新確認需求、程式與外部套件現況，不把候選方案視為已決定的規格。

初期 adapter 移植 Maverick 的六項適用門檻規則，保留固定來源版本與 MIT 授權，沒有安裝整個上游 server。 DiagnosticProvider 接收原生績效與觀察值；替換入口及證據模型擴充方式見 ARCHITECTURE.md「診斷擴充與替換」。目前沒有完成市場情境或波動敏感度的因果診斷，研究建議仍待驗證，也不自動授權下一個實驗。

外部 LLM 整理可編輯的研究摘要，後端提供版本檢查、保存與封存。ZIP 包含 HTML、JSON 與所引用報告，任何階段都可產生，沒有逐字聊天攔截器。 這只完成可保存、續讀與分享的 PoC；跨研究搜尋與自動追蹤假說尚未實作。研究核心不綁定對話模型供應商，參考方向仍可包含 QuantConnect project memory。

不預先規定整個自動開發系統。初期可由人選擇案例，再讓開發助手提出改進。元件更新後，仍要能解釋舊實驗引用的版本。

先區分訊號投票、獨立淨值加權、配置最佳化和共享帳戶。初始配置後讓權重漂移，與每期固定權重再平衡也不同。此頁記錄目標，不要求現在完成這些設計。

保留研究服務責任，不代表凍結目前的訊號契約。若需要事件、委託與成交回報，應允許原生事件策略設計。其他候選依需求再調查，例如 order book/多 venue 需求才評估 NautilusTrader。

具體是 DefaultBrokerageModel 的 NullSlippageModel，不是說 LEAN 無法模擬滑價。部分成交、流動性等可自訂，代價是仍須設定與驗證模型。

不把缺口重複鋪陳成警告清單。真正開始多人產品開發時，再確認權限、隔離、配額與工作排程需求。

不承諾所有 TODO 都一定做。把對話模型與產品計費留在外部，是責任分工；多人服務必需的隔離則不能用自由度為理由省略。
